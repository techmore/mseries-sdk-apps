# SDK audit and direction (2026-10-23)

Scope: the SDK as it stood on `dev` after the greeter work: the `msdk` crate (vocabulary and checker), the existing
guidance in [RUST-PANTHEON-SDK.md](RUST-PANTHEON-SDK.md) and [APP-BUILDING-GUIDE.md](APP-BUILDING-GUIDE.md), and the first two consumers
(the greeter, and the dock being started). Written against the owner's goals stated in this session.

## 1. Goals the audit measures against

1. **The SDK builds all core apps** unless an app is very hard; the language guides development end to end.
2. **A small local model (Qwen ~4B) reads the API and recreates the core apps.** This is the SDK's acceptance test: the six
   [sdk-bench specs](sdk-bench/specs) are exactly that test. "Complete" means the model passes them.
3. **Real-time rendering with a code back end:** change the description, see the app change live; a visual editor is welcome.
4. **One stack, one compiler:** Rust only; a pinned toolchain and one shared build cache, so builds stay fast.
5. **Output is Rust objects** (typed state and message types a Rust developer or agent can extend), compiled to the native
   GTK4/Granite look; HIG rules are enforced, not remembered.
6. Shell surfaces (dock, panels, greeter, dialogs) are SDK apps too.

## 2. Findings

| # | Finding | Why it matters | Status |
|---|---|---|---|
| 1 | State had no record types; lists were untyped, so row templates (`{title}`) and messages were unchecked | The two most common model mistakes went undetected | **Fixed:** `types`, `list<Record>`, typed message payloads |
| 2 | Only one window could be described | Dock, panels, popovers, dialogs and the greeter are separate roles in the compositor protocol | **Fixed:** `surfaces` of kind window, dialog, popover, panel (anchor, size, hide mode), fullscreen |
| 3 | The language described a screen but not behaviour | "The language guides development" needs logic, or every app falls back to hand-written Rust | **Fixed (v0):** `update` rules (`set`, `toggle`, `append`, `patch`, `remove`, `clear`, `call`, `toast`, `open`, `close`, `quit`, `when`), named `services`, live `feeds`, `persist`; `"logic": "rust"` for hard apps |
| 4 | Checker, vocabulary dump and any grammar could drift | A small model needs one source of truth | **Fixed:** `vocab.rs` holds every table; checker, JSON Schema (`msdk schema`) and prompts derive from it |
| 5 | HIG rules were prose in a skill | Nothing rejected a non-HIG screen | **Fixed (first set):** destructive needs confirm, one primary action visible at once, no password in messages, labels, empty states, stable list keys; shared design tokens (`msdk tokens`) |
| 6 | **No renderer: nothing shows a running screen from a description** | Violates the owner's own "running example within about 30 minutes" rule and blocks goals 3 and 6 | **Fixed (first cut):** `msdk-gtk` / `msdk-run app.ui.json --watch` renders every component, runs the rules, calls services, persists state and live-reloads; Quick Notes runs from its description. The greeter front end is still hand-written and moves onto it next |
| 7 | No code generation to Rust objects | Goal 5 | **Open:** `msdk gen` emits `State`, `Msg`, a `Logic` trait stub and the view as Rust |
| 8 | No `msdk shot` / `pack` / `run --watch` | Verify loop and delivery | **Open:** `run --watch` and `shot` come with the renderer |
| 9 | Diagnostics have JSON paths but no line numbers | Humans and editors want lines | Low priority; `--json` output added |
| 10 | No benchmark has been run | Goal 2 is unmeasured | Deferred by the owner to the decision point; the specs and rubric exist |

## 3. Conflict with existing guidance (needs the owner's call)

[RUST-PANTHEON-SDK.md](RUST-PANTHEON-SDK.md) and [APP-BUILDING-GUIDE.md](APP-BUILDING-GUIDE.md), written after the Signal/Messages feedback on
2026-10-22, say: *extract the SDK from demonstrated needs; avoid a description language until a measured repeated need justifies its
maintenance cost; a generator is a desired deliverable, not an existing command.*

The owner's direction today is the opposite on the first two points: the language is the primary way to build apps. What I
recommend keeping from that guidance, and what I recommend changing:

- **Keep:** show a running primary flow early; report implemented / built / installed / loaded / reviewed / accepted separately; no
  unsupported completion percentages; honest "not done"; incremental debug builds with a shared cache; preserve existing services.
- **Change:** replace "avoid a description language" with "the description language is the primary authoring surface; `Custom` and
  `logic: rust` are the escape hatches, and every use is recorded as a gap". The 12-hours-to-50% report is the stated need.

I have not edited those two files; they are referenced by `AGENTS.md` and are the owner's to change.

## 4. The language question: steal concepts, keep one canonical form

The owner asked whether to adopt an existing language. Recommendation:

| Borrow | From | Where it shows up |
|---|---|---|
| **The Elm architecture** (`state`, `messages`, `update`, `view`) | Elm; Relm4 and iced in Rust | The core model of every app; already the shape of the format |
| **Component names and modifiers a model already knows** | SwiftUI and QML (both heavily represented in model training data) | Rename toward familiar terms where it is free (for example `Toggle`, `TextField`, `List`, `NavigationSplitView`) after the benchmark shows which names the model gets right |
| **GTK-native declarative output** | Blueprint (GNOME's UI markup that compiles to GtkBuilder XML) | An optional release-mode target; the interpreter and the Rust generator are the main paths |
| **Typed Rust objects from a schema** | `serde`/`schemars` style derive | `msdk gen`: the document's `types`, `state`, `messages` become Rust structs and enums |
| **Constrained decoding** | JSON Schema to grammar | Why the canonical form stays JSON: a grammar generated from `msdk schema` forces structurally valid output from a 4B model |

A friendlier surface syntax (SwiftUI-like or QML-like text) can sit on top later and compile to the same JSON. Adding it before the
benchmark would be guessing; the decision point is "does the model do better on syntax X", which is one small run on SER8.

## 5. Real-time rendering and the visual editor

The path to goal 3 is one component, the **interpreter runtime** (`msdk-gtk`): it loads a description, renders it with GTK4,
runs the `update` rules (or a Rust `Logic`), re-renders on every state change, and **reloads the view when the file changes**
without recompiling anything. `msdk run app.ui.json --watch` is the fast loop for people and for a 4B model; `msdk shot` renders
headless for a vision check. The same runtime, pointed at the compositor's panel and greeter roles, runs the dock and the greeter.

The **visual editor** ("Studio") is then an ordinary SDK app on top of it: code on one side, the live preview on the other, a
component palette, and click-to-select that maps a rendered widget back to its JSON path (the checker already speaks JSON paths).
It is the first large dogfood app and should not start before the runtime renders the greeter.

One toolchain: a pinned stable Rust in `rust-toolchain.toml`, one shared `CARGO_TARGET_DIR` (already `~/.cache/cargo-target`), the
interpreter built once; app iteration in dev mode never compiles. Release mode generates Rust and builds with the same toolchain.

## 5b. The loop a small model runs (built)

The owner's picture: the model does not guess, it looks around, asks, gets help, and ends at gates it can audit. The CLI is that
loop's tool surface; every answer is derived from the same tables the checker uses, so it cannot be stale.

| Need | Command | Answers |
|---|---|---|
| "What can I use?" | `msdk describe` | Catalogue of components, surfaces, services, feeds, enums, actions |
| "How do I use X?" | `msdk describe Button` | Properties with kinds and required flags, plus a minimal valid example (also services, feeds, enums) |
| Autocomplete / "what goes here?" | `msdk complete app.ui.json /surfaces/main/body/children/0/on` | Valid next keys for an object, or valid values for a property: enum values, state keys of the right type, messages with the right payload, record fields visible in a List row |
| "What does this error mean?" | `msdk explain <code>` | One paragraph and the usual repair for each of the checker's codes |
| "Is it valid?" | `msdk check --json` | Every problem with JSON path, code, message and a fix suggestion |
| "Is it done?" | `msdk gate app.ui.json app.gates.json` | Built-in gates (checker clean, every message has a rule) plus scripted scenarios run headless; a JSON audit log of pass, fail and why |

The editor ("Studio") uses the same calls for autocomplete and hover help, which is what makes it feel like Xcode: nothing it
offers can be invalid. The acceptance test for the SDK is this loop, driven by Qwen ~4B, passing the gates of the six sdk-bench specs.

## 6. Order of work

1. This change: typed core, surfaces, update rules, services, feeds, schema, tokens, HIG lints (done, 17 checker tests).
2. `msdk-gtk` runtime: **built**; next, render the greeter from `greeter.ui.json` (replacing its hand-written front end), then the dock; panel anchoring needs the Pantheon shell protocol client.
3. Dock logic (pins, resolver, window feed) as a Rust `Logic`; compositor foreign-toplevel feed behind `windows.list`.
4. `msdk gen` (Rust objects) and `msdk pack` into the package repo.
5. Studio.
6. Benchmark the six specs with Qwen ~4B on SER8 and tune the vocabulary, names and error messages from what it gets wrong. The
   owner asked to measure only at decision points; this is the one that decides the language.
